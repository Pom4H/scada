# Проверка серверных сценариев и редактора

Первый сквозной результат проверен на работающем приложении: TS-ссылка открывает схему, два браузера подключаются к одному серверному прогону, наблюдают деградацию, обслуживание и замену насоса. Реальный разрыв SSE переводит показания в неизвестные; после восстановления приходит полный снимок. Запись воспроизводится и сравнивается с нормальным прогоном. TS и история редактирования не изменяются от сигналов.

## Воспроизводимые проверки

| Проверка | Локальный результат |
|---|---|
| `npm run check` | Все сборки и strict TypeScript; 38 core + 9 моделей сервера + 17 независимых API/client + 14 adversarial core + 7 лабораторных тестов — пройдены |
| Существующий editor Playwright, Chromium | 18/18 |
| Adversarial browser, Chromium | 7/7; прежние дефекты вложенных приборов, истории и неизвестных значений устранены |
| `npm run test:runtime:e2e` | Единый прогон 8/8, около 1.6 минуты |
| `npm audit --audit-level=high` | 0 уязвимостей на момент проверки |
| Реальный capture | 8 PNG, 44.96-секундное видео, 0 ошибок браузера, сохранность TS после 400 обновлений |

Runtime acceptance покрывает не только удачное подключение: два клиента сверяют общий seq и сигналы; сетевой прокси физически обрывает поток; исходная вкладка закрывается, пока другой клиент продолжает наблюдение; запись играет отдельно от эфира. Проверяются права view/operator/research, отсутствие private fault truth в публичных данных, идемпотентность команд, неправильные типы и диапазоны, SQLite restart, повторяемость seed и расписания команд, смена экземпляра, несовместимая конфигурация и запоздавший ответ создания прогона после правки TS.

Отдельный фильтр подключён через общие metadata/behavior/SVG/3D registration points. API-тест проверяет его поведение и clean-команду; реальные кадры показывают его 2D/3D-геометрию. Дополнительные тестовые типы регистрируются без изменения центрального компилятора и планировщика.

GitHub Actions в [PR #11](https://github.com/Pom4H/scada/pull/11/checks) выполняет полный набор на Node из `.nvmrc`, включая Chromium и WebKit для редактора и adversarial browser. Локально WebKit не был установлен; его результат проверяется по CI, а не предполагается из Chromium. Runtime 3D acceptance выполняется в Chromium со SwiftShader. Публикация Pages требует отдельного ручного запуска; эти проверки не выполняют production-деплой.

## Влияние на редактор

Окружение: Linux x64, AMD EPYC 9V74, 8 доступных CPU, Node **24.19.0**, Chromium **149.0.7827.0**, viewport **1440×900**. Локальный Node немного ниже `engines`; CI отдельно использует закреплённый Node 24.20.0. До: код приложения PR #10 `8435e665…` (его разрешение merge не меняло приложение). После: `720e1bfd…` с финальной подписью инспектора; JSON честно помечен `workingTreeDirty: true`, поскольку evidence добавлялись следующим коммитом.

Один и тот же seed=42 и стенд: 5 изменений параметра и 3 изменения координаты после прогрева на каждой схеме; таблица показывает медианы синхронных операций редактирования. Это небольшая воспроизводимая выборка, не статистическая гарантия для другого устройства.

| Элементов / связей | Параметр до, мс | После, мс | Координата до, мс | После, мс |
|---|---:|---:|---:|---:|
| 8 / 7 | 3.9 | 5.6 | 8.9 | 13.2 |
| 16 / 15 | 6.0 | 6.8 | 17.4 | 17.3 |
| 32 / 31 | 10.7 | 14.0 | 166.0 | 39.2 |
| 48 / 47 | 13.8 | 14.3 | 897.1 | 108.1 |

Замена сортировки очереди A* на heap дала около **8.3×** ускорения изменения координат на сложной 48-элементной схеме. На маленькой схеме дополнительные контракты/UI добавили около **1.7 мс** для параметра и **4.3 мс** для координаты. Редактирование 48 элементов всё ещё может блокировать главный поток примерно на 0.1 секунды.

В обоих замерах сохранены DOM-идентичность ротора и undo/redo. На 180 idle-интервалах 2D rAF p95 составил 16.7 мс; 48-элементная схема: 16.8 → 16.7 мс. Эти интервалы измерены отдельно от синхронного перетаскивания. Загруженный исходный JS вырос приблизительно на 62 КБ (без сжатия); Three в начальных запросах отсутствует и загружается при выборе 3D. Полные данные: [до](evidence-runtime/editor-before.json), [после](evidence-runtime/editor-after.json), [сравнение](evidence-runtime/editor-comparison.json).

## Анимация и сервер

При двух активных серверных прогонах, 8 устройствах и 5 связях один браузер без записи экрана показал:

| Представление | Медиана rAF, мс | p95, мс |
|---|---:|---:|
| SVG 2D | 16.7 | 16.7 |
| WebGL 3D, программный SwiftShader | 50.0 | 133.3 |

3D: 30 778 треугольников, 312 draw calls; 20 прогревочных и 90 измеренных интервалов. При параллельной записи экрана p95 увеличился до **316.6 мс**. Программный WebGL в этом окружении не даёт стабильно плавных 60 fps. Аппаратный GPU не проверен, поэтому обещания его FPS нет. [Полный замер без recorder](evidence-runtime/animation-without-recording.json).

Сервер отдельно: 48 элементов, 8 насосов, 40 связей; SQLite WAL/FULL; 300 шагов после 20 прогревочных. Медиана **0.657 мс**, p95 **1.101 мс**, максимум **3.303 мс** при шаге 100 мс. Снимок 18 190 байт; 321 сохранённый кадр занимал около 5.85 МБ. Это результат данного CPU/диска. Подробные допущения и расход хранения описаны в [серверном руководстве](server-runtime.md).

## Оставшиеся границы

- Модели синтетические: последовательные установки, без гидравлического решения, PLC и обучения диагностических моделей.
- 3D — пространственный просмотр и выбор; размещение берётся из 2D. На тесной схеме подпись может закрывать часть собственной геометрии.
- До 48 элементов в редакторе и 100 сохранённых прогонов на локальном сервере. Полные кадры без retention/агрегации не подходят для многолетнего хранения без следующего этапа.
- Роли действуют на весь сервер, без project ACL. Автоматической миграции сохранённого поведения нет; несовместимая версия явно блокирует продолжение архива.
- Большие сцены, аппаратный WebGL, длительные испытания на разных ОС и реальные промышленные данные этим стендом не подтверждены.
