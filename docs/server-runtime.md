# Серверные прогоны

Сервер исполняет установленные модели оборудования с шагом 100 мс и записывает каждый кадр в SQLite. Браузеры получают одинаковые сигналы одного прогона. Закрытие вкладки, пауза анимации и просмотр записи не останавливают исполнение. Демонстрация использует синтетическое оборудование; драйверов PLC и команд реальным устройствам в ней нет.

## Запуск

Нужен Node из диапазона `engines` в `package.json` — Node 24.20.x или новее в ветке 24. Встроенный `node:sqlite` используется без дополнительного сервера БД.

```sh
npm ci
npm run demo
```

Откройте `http://127.0.0.1:4175/scada/`. Процесс напечатает три случайных токена. Вставьте нужный токен в панель подключения. При создании схемы или ссылки он не включается в TS; браузер хранит его только в памяти текущей вкладки. Программный запуск доступен через `startServer(options)` из `server/index.ts`; импорт этого модуля сам по себе не запускает сеть или таймер.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `SCADA_HOST` | `127.0.0.1` | Адрес привязки HTTP-сервера |
| `SCADA_PORT` | `4175` | Порт |
| `SCADA_DATA_PATH` | `data/runs.sqlite` | Устойчивое хранилище прогонов |
| `SCADA_STATIC_DIR` | `dist` | Каталог собранного редактора |
| `SCADA_ALLOWED_ORIGINS` | пусто | Дополнительные точные browser origins через запятую; свой origin разрешён |
| `SCADA_VIEW_TOKEN` | случайный | Чтение публичных данных всех прогонов |
| `SCADA_OPERATOR_TOKEN` | случайный | Чтение, создание, команды оборудования, завершение записи |
| `SCADA_RESEARCH_TOKEN` | случайный | Права оператора плюс исходные условия и скрытое состояние модели |

Для постоянных учётных данных задайте все три токена через окружение. Если они не заданы, при новом запуске процесса генерируются новые; сохранённые прогоны остаются в БД, а вкладкам потребуется новый токен. Частично заданный набор токенов или одинаковые токены не принимаются. Для отдельного локального frontend dev server можно явно задать `SCADA_ALLOWED_ORIGINS=http://127.0.0.1:4173,http://localhost:4173`.

Роли общие для этого локального приложения: разграничения по пользователям, проектам и организациям пока нет. HTTP слушает loopback по умолчанию. Перед сетевым размещением потребуются TLS, управление секретами и прикладная модель доступа; этот этап не выполняет production-деплой.

## API

Все запросы к `/api`, кроме health, передают `Authorization: Bearer …`. POST создания и команд используют `Content-Type: application/json`. Токены в query string не поддерживаются. Межсайтовые запросы разрешаются только для настроенных origins.

| Метод и путь | Результат / доступ |
|---|---|
| `GET /api/health` | Публичные status, synthetic и stepMs |
| `GET /api/runs?projectId=…` | `{runs}` — публичные краткие сведения |
| `POST /api/runs` | `{projectId, source, scenario, seed?, label?}` → `{run, snapshot}`; оператор |
| `GET /api/runs/:id` | `{run, snapshot}` |
| `GET /api/runs/:id/events?after=N` | SSE с событиями `frame` и `id: seq`; первая запись — полный актуальный snapshot |
| `POST /api/runs/:id/commands` | `{commandId, equipmentId, command, value?}` → `{commandId, accepted:true, seq}`; оператор |
| `POST /api/runs/:id/complete` | Последний кадр с `run.completed`, остановка записи и `{run, snapshot}`; оператор |
| `GET /api/runs/:id/history?after=N&limit=500` | `{frames, nextAfter, hasMore}`; кадры строго после N |
| `GET /api/runs/:id/replay?seq=N` | Точный сохранённый кадр N, помеченный snapshot |
| `GET /api/runs/:id/research?after=-1&limit=500` | Версионный manifest, текущие hidden states, команды и частные события; исследователь |

`history` принимает `after >= -1`, `limit` от 1 до 1000. `after=-1` включает начальный кадр №0. `replay` требует существующий целочисленный seq. В исследовательском ответе `after` и `limit` относятся к журналам команд и частных событий; manifest и hidden относятся к текущему checkpoint.

Пример создания через обычный JSON-клиент:

```json
{
  "projectId": "pump-line",
  "source": "import {tank,pump,outlet,connect} from \"@scada/core\"; const t=tank(\"T\",{x:0,y:0,level:80}); const p=pump(\"P\",{x:250,y:0,rpm:1500}); const o=outlet(\"O\",{x:600,y:0}); connect(t.outlet,p.inlet); connect(p.outlet,o.inlet);",
  "scenario": "degradation",
  "seed": 42,
  "label": "Прогон 1"
}
```

Команда обслуживания — `{"commandId":"service-001","equipmentId":"P","command":"service"}`. Сервер проверяет зарегистрированную команду, тип и диапазон значения. Повтор того же commandId с тем же содержимым возвращает прежний receipt без повторного исполнения, в том числе после перезапуска и завершения прогона. Другое содержимое с прежним ID возвращает 409. Завершение прогона идемпотентно; новые команды после него возвращают 409.

Кадры содержат идентификатор прогона, seq, время, позиции и экземпляры оборудования, фактические режимы, показания с типом/единицей/качеством и расход по связям. `null` означает неизвестное показание; подтверждённый нулевой расход равен числу 0 с quality good. Неизвестный расход не участвует в анимации как нулевое измерение. Причина повреждения крыльчатки, wear, integrity, seed и scenario находятся в исследовательской части. Публичные названия прогонов должны быть нейтральными при слепой проверке диагностики: свободный пользовательский label сам по себе может раскрывать метку сценария.

SSE использует полные кадры. После разрыва сервер сразу выдаёт последний полный snapshot; пропущенные исторические кадры доступны через `history`. Heartbeat передаётся каждые 5 секунд, включая завершённый прогон. Отдельный поток не может удерживать исполнение модели: медленный подписчик отключается при накоплении более 1 МиБ исходящих данных.

## Время, запись и восстановление

`simTimeMs` растёт на 100 мс за модельный шаг. `timestamp` равен эпохе создания плюс модельное время. Команды создают следующий seq в текущий момент модельного времени. Одинаковые исходник, epoch, seed и порядок команд воспроизводят те же кадры; PRNG и скрытое состояние входят в checkpoint. При программном тестировании `engine.create(input,{id,epoch})` задаёт фиксированные ID и эпоху, а `engine.stepAll()` выполняет ровно один шаг всех активных прогонов.

SQLite работает в WAL с `synchronous=FULL`. Кадр, checkpoint, manifest и связанная команда записываются одной транзакцией. После перезапуска исполнение продолжается с последнего подтверждённого шага. Время, пока сервер не работал, не догоняется. Поэтому доступность соединения проверяется по времени получения данных, отдельно от часов модели.

В manifest сохранены исходный TS, хеш конфигурации, хеш точного документа, версии behavior и metadata, правила установки, исходные экземпляры, допущения моделей и seed. `sourceHash` вычисляется по каноническим узлам/связям, поэтому добавление `runtime.run` или переименование TS-переменной не создаёт другую установку. `configurationVersion` — SHA-256 точного исходника. Замена меняет `instanceId`, сохраняя `positionId`; обслуживание сохраняет экземпляр. Частный журнал замены содержит прежний и новый instanceId.

При несовпадении установленной версии поведения или metadata с сохранённым прогоном сервер отказывается незаметно продолжать его другой моделью. Автоматической миграции старых моделей пока нет; для чтения такого архива нужен совместимый комплект установленных версий. Перед заменой версии или переносом сервера сохраните БД штатным SQLite backup либо копированием после остановки процесса. Копирование только основного файла активной WAL-БД может потерять последние записи.

## Модели и допущения

Серверный реестр устанавливается в `server/models.ts`. Планировщик в `server/engine.ts` не содержит веток по типу насоса или фильтра: он вызывает initialize/advance/output/command установленной модели и применяет общие правила её process outputs.

Для первой установки поддерживается последовательная линия: один источник, один привод, один выход и произвольное число пассивных компонентов. `driverFlow` привода умножается на conductance остальных компонентов; available=false источника даёт подтверждённый ноль. Оборванные линии, ответвления, петли и несколько приводов в одной связанной установке дают неизвестный расход и явное событие ограничения. Независимые последовательные линии поддерживаются.

| Модель | Явное поведение |
|---|---|
| Насос | Задержка `startDelay`, затем разгон/торможение 1500 rpm в секунду. Номинальный расход `nominalFlow × rpm / 1500 × integrity`. Вращение двигателя отделено от передачи усилия крыльчаткой. |
| Деградация насоса | В синтетическом degradation-сценарии разрешена с 5-й секунды модельного времени; wear растёт на `degradationRate` в секунду только при ненулевых rpm. До wear 0.85 integrity равна `1 − 0.85 × wear`; при достижении порога крыльчатка считается повреждённой и integrity становится 0.04. |
| Измерения насоса | Вибрация растёт с rpm, wear и повреждением; добавляется небольшой seeded noise. Температура приближается к синтетической целевой с постоянной времени 5 секунд. Alarm warning при вибрации ≥4.5 mm/s, trip при ≥10 mm/s. Alarm не подменяет команду остановки двигателя. |
| Обслуживание | Команда service переводит насос в maintenance на `maintenanceSeconds`, тормозит двигатель, восстанавливает исправность в том же экземпляре насоса и возобновляет ранее заданный режим с задержкой запуска. Следующая деградация имеет 5 секунд отсрочки после обслуживания. |
| Замена | Команда replace устанавливает новый instance на той же позиции, с исправной крыльчаткой и заново запущенной задержкой. |
| Резервуар | Синтетическая ёмкость 10 м³. Уровень изменяется от расхода и ограничен 0–100%; автоматического пополнения нет. |
| Клапан | Привод перемещается на 40 процентных пунктов в секунду; conductance = opening / 100. Это условная характеристика. |
| Фильтр | Conductance = 1 − resistance. Условный перепад давления = `2 × resistance × abs(flow) / 12` bar. Clean сбрасывает resistance. |
| Теплообменник и приборы | Идеальный нагреватель задаёт выходную температуру; подключённые приборы читают транспортные каналы. Давление — условная величина, без гидравлического решения. |

Эти коэффициенты демонстрационные и не получены из реальных архивов. Механика отказа не обучена на данных; диагностика и подбор параметров на независимой многолетней истории остаются последующим этапом. Записанные версии, входы, команды, экземпляры и скрытая разметка создают для него воспроизводимую основу.

## Подключение поведения компонента

Фильтр показывает минимальный пакет: `src/components/filter/definition.ts`, `behavior.ts`, `visual.ts`. Metadata регистрирует параметры, порты, команды и типизированные сигналы. Behavior реализует методы `BehaviorDefinition` из `server/behavior.ts` и регистрируется в композиции `installedBehaviors()`. Представления устанавливаются в своих реестрах. Ни компилятор, ни серверный планировщик не получают специального случая filter.

```ts
registry.register({
  kind: 'restrictor', // metadata этого типа уже установлены
  version: '1.0.0',
  assumptions: ['Синтетическое постоянное сопротивление'],
  initialize: () => ({}),
  advance() {},
  output: (_state, context) => ({
    mode: 'ready', alarm: 'none',
    signals: { observed: context.transport.flow },
    process: { boundary: 'inline', conductance: 0.25 },
  }),
});
```

Использование в TS — `component("restrictor", "R-1", {x:400,y:100})`. Документ описывает установку; он не импортирует исполняемую модель с URL и не выполняет callback. Проверка в `tests/server-model.test.ts` устанавливает отдельный тестовый restrictor через публичные metadata/behavior API и получает ожидаемый расход без правок компилятора или планировщика.

## Проверки и пределы

`npm run test:runtime` запускает модельные и независимые контрактные проверки. Они покрывают одинаковые кадры при одинаковых входах, повреждение и обслуживание насоса, замену экземпляра, независимое расширение, SQLite restart, идемпотентность, завершение записи, роли, восстановление SSE и точное воспроизведение кадров.

Сервер ограничивает число сохранённых прогонов до 100, одновременных SSE-подписчиков до 64, JSON body до 512000 байт, документ до 120000 символов, сцену до 48 элементов. Пока нет удаления/автоматической очистки прогонов, downsampling, сжатия истории, отдельного архивного хранилища, multi-tenant доступа и распределённого исполнения. Завершайте ненужные активные записи: каждый полный кадр остаётся в БД.

Измерение в контейнере Linux 6.18.35, AMD EPYC 9V74, Node 24.19.0: один прогон из 48 элементов, 8 насосов и 40 связей; 20 шагов прогрева, затем 300 измеренных шагов, SQLite WAL/FULL. Версия Node в окружении измерения на один патч ниже заявленного диапазона проекта; воспроизведение на Node 24.20.x здесь не проверялось.

| Измерение | Результат |
|---|---:|
| Медиана шага с записью | 0.657 мс |
| p95 | 1.101 мс |
| Максимум | 3.303 мс |
| Период модели | 100 мс |
| Размер полного snapshot | 18190 байт |
| SQLite после 321 кадра и checkpoint | 5853184 байт |

Замер включает модели, транспортные правила и транзакционную запись, без HTTP-подписчиков и рендеринга. Это результат данного окружения, не оценка пользовательского ноутбука или промышленных нагрузок. При таком размере кадров 10 Гц дают около 0.65 ГБ JSON в час до накладных расходов хранения. Многолетний архив потребует политики хранения и агрегации; воспроизводимая демо-запись сохраняется полностью.
